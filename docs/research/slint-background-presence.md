# Running a Slint app in the background on Linux: tray, hidden window, autostart, notifications

Research for [What does it take for a Slint app on Linux to run in the background?](https://github.com/tobytaken/prism-electron/issues/116). It feeds [Does Prism keep running in the background, and who notifies the user?](https://github.com/tobytaken/prism-electron/issues/117), part of the [native Prism map](https://github.com/tobytaken/prism-electron/issues/96).
Gathered 2026-10-10 from primary sources: Slint 1.18.1 source, ksni and tray-icon source, the xdg-desktop-portal specs and frontend source, the GNOME and KDE portal backends, the freedesktop notification and autostart specs, the Flatpak docs, the Flathub linter, and the code, wikis and trackers of LACT, CoreCtrl, GameMode, power-profiles-daemon and earlyoom. Section 6 adds a small measurement run on this machine. Every claim links to its source. Measured numbers say where they were measured, and numbers that weren't measured are marked as such.

## Answer in one paragraph

Slint 1.18.1 has every piece a background app needs: closing a window hides it by default, `Window::hide()`/`show()` keep the component and its state, `run_event_loop_until_quit()` keeps the loop alive with no window, and the `SystemTrayIcon` element (since 1.17.0) adds a tray icon through `ksni` (StatusNotifierItem). The tray adds about 1.1 MB to the binary and roughly 1–1.5 MiB of PSS. It shows on KDE, COSMIC and wlroots bars such as waybar, and on GNOME only with the AppIndicator extension, which Ubuntu ships and Fedora does not. **In a Flathub Flatpak, Slint's own tray won't register**, because Slint's ksni backend always claims the `org.kde.StatusNotifierItem-PID-N` bus name and Flathub doesn't allow that ownership. The workaround is `tray-icon` (ksni backend) or `ksni` directly with `disable_dbus_name`. **A hidden window saves nothing measurable** over a visible or minimized one, since none of them render. A process that has never shown its window is about 6 MiB PSS and 9 MiB VRAM smaller, but in Slint 1.18.1 such a window doesn't draw its first frame on Wayland until the app calls `request_redraw()`. Autostart is an XDG autostart file for native packages and the Background portal for Flatpak. Only GNOME and KDE implement that portal, and GNOME lists only Flatpak apps as "background apps". Desktop notifications work from the GUI through `notify-rust` (adds about 0.3 MB) or through the Notification portal (`ashpd`). Buttons and clicks reach the app only while it is running, unless the app is D-Bus-activatable and uses the portal's `app.` actions. **`prismd` can't notify the desktop on its own** without switching into each user's session bus. None of the comparable projects does that. They all leave the desktop side to a process inside the user's session: the GUI, a per-user daemon or a small relay agent. A windowless `notify-rust` sender measured 2.0 MiB PSS.

## 1. Tray icon

### Slint already has one: `SystemTrayIcon`

- **Since 1.17.0 (2026-06-24):** "Added new `SystemTrayIcon` element." [CHANGELOG](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md). 1.18.0 fixed `show()`/`hide()` on tray components and "report[s] an error when no system tray backend is available" (same file).
- **Cargo feature:** `system-tray` is in Slint's default features and maps to `i-slint-core/system-tray`, which pulls in `ksni` 0.3 (`async-io` + `blocking`) on Linux/BSD. [api/rs/slint/Cargo.toml](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/slint/Cargo.toml), [internal/core/Cargo.toml](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/Cargo.toml). The toolkit spike built Slint with `default-features = false` and without `system-tray` ([spike Cargo.toml](https://github.com/tobytaken/prism-electron/blob/prototype/toolkit-spike/prototypes/toolkit-spike/slint/Cargo.toml)), so Prism has to add the feature explicitly.
- **API:** a component inherits `SystemTrayIcon`. It has `icon`, `tooltip`, `title` and `visible` properties, a `clicked` callback, and exactly one `Menu` child. It must be the root of an exported component, not a child of a `Window`. [Slint docs: SystemTrayIcon](https://docs.slint.dev/latest/docs/slint/reference/window/systemtrayicon/), compiler tests [systemtray.slint](https://github.com/slint-ui/slint/blob/v1.18.1/internal/compiler/tests/syntax/elements/systemtray.slint) and its siblings.
- **It fits the event loop:** ksni runs its D-Bus service on its own thread, and Slint forwards clicks and menu activations through a channel to a task on the Slint event loop. [ksni.rs L84–L93, L270–L289](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/items/system_tray/ksni.rs#L84-L93). No GTK main loop is needed.
- **It keeps the process alive:** a visible tray icon counts as a "keepalive", just like a visible window. `run_event_loop()` "will run until the last window is closed and the last visible system tray icon is hidden". [context.rs L314–L331](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/context.rs#L314-L331), [slint lib.rs L243–L265](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/slint/lib.rs#L243-L265).
- **Limits of the Linux backend in 1.18.1** (all from [ksni.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/items/system_tray/ksni.rs)):
  - The icon is always a pixmap (`icon_pixmap`, L61). There are no themed or symbolic icon names ([slint#12360](https://github.com/slint-ui/slint/issues/12360), open).
  - The SNI `Id` is hard-coded to `"slint-tray"` (L39).
  - Menu entries become plain `StandardItem`s (L83–L97). `MenuEntry` has `checkable`/`checked` fields ([builtin_structs.rs L191–L194](https://github.com/slint-ui/slint/blob/v1.18.1/internal/common/builtin_structs.rs#L191-L194)), but the tray drops them. A "Pause automatic switching" toggle would therefore have to change its label instead of showing a check mark.
  - `tray.spawn()` (L263) uses ksni's defaults: it **owns a well-known bus name** and **fails immediately when no tray host exists** (see below). A failure is only `debug_log!`ged ([system_tray.rs L304–L313](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/items/system_tray.rs#L304-L313)). The app gets no signal that its icon isn't shown, and nothing retries if a host appears later (for example, waybar starting after Prism).
  - Known bug: if the host reads the menu before Slint fills it in, GNOME's AppIndicator extension (before v62) shows an empty menu for the rest of the process's life ([slint#13624](https://github.com/slint-ui/slint/issues/13624)). The fix ([slint#13693](https://github.com/slint-ui/slint/pull/13693), merged 2026-09-29) isn't in a release yet. The latest is 1.18.1, from 2026-09-21. The same report notes that calling `hide()` on a tray whose `visible` isn't bound in `.slint` panics with "Constant property being changed", so Prism should bind `visible` to a property.

### Which desktops show it

StatusNotifierItem needs a `org.kde.StatusNotifierWatcher` and a host on the session bus.

| Desktop | Tray host | Notes |
|---|---|---|
| KDE Plasma | Built in | SNI is KDE's own protocol ("KDE's blessed successor of the systray", [AppIndicator extension README](https://github.com/ubuntu/gnome-shell-extension-appindicator/blob/master/README.md)). |
| GNOME (upstream, Fedora Workstation) | **None** | Needs the [AppIndicator and KStatusNotifierItem Support](https://github.com/ubuntu/gnome-shell-extension-appindicator) extension (supports Shell 45–51 per its `metadata.json`). Fedora Workstation declined to ship it and wants a new freedesktop spec instead ([fedora-workstation#246](https://pagure.io/fedora-workstation/issue/246), closed 2026-02-04). The extension **doesn't show tooltips** ("the GNOME designers decided not to have tooltips in the shell", README), so live vitals in a tooltip would be invisible there. |
| GNOME on Ubuntu | `ubuntu-appindicators@ubuntu.com` | Installed by default on this Ubuntu 26.04 machine (`/usr/share/gnome-shell/extensions/`). In the measurement run (section 6), it registered Slint's item: `RegisteredStatusNotifierItems = ["org.kde.StatusNotifierItem-975675-1"]`. |
| Hyprland, sway | Only if a bar with a tray runs | waybar's `tray` module owns `org.kde.StatusNotifierWatcher` itself ([watcher.cpp](https://github.com/Alexays/Waybar/blob/master/src/modules/sni/watcher.cpp)) and is documented as "still in beta" ([waybar-tray(5)](https://github.com/Alexays/Waybar/blob/master/man/waybar-tray.5.scd)). Without a bar, there's no tray. |
| COSMIC | Status area applet | `cosmic-applet-status-area` implements the watcher ([source](https://github.com/pop-os/cosmic-applets/tree/master/cosmic-applet-status-area/src/subscriptions/status_notifier_watcher)). Not tested. |

With no watcher or no host, ksni's `spawn()` returns `Error::Watcher`/`Error::WontShow` unless `assume_sni_available(true)` is set. In that case the error goes to `Tray::watcher_offline`, and the item registers once a host appears. [ksni blocking.rs L69–L84](https://github.com/iovxw/ksni/blob/master/src/blocking.rs#L69-L84), [ksni lib.rs](https://github.com/iovxw/ksni/blob/master/src/lib.rs). Slint doesn't set it. An app that hides its window to the tray must check for itself that a host exists (`IsStatusNotifierHostRegistered` on the watcher, [spec XML](https://github.com/iovxw/ksni/blob/master/spec/StatusNotifierWatcher.xml)). Otherwise closing the window leaves the user with no visible way back.

### Flatpak

- "To use StatusNotifier, you must at least have the `--talk-name=org.kde.StatusNotifierWatcher` permission to register an item. Depending on the exact implementation … it may need session bus ownership of `org.kde.StatusNotifierItem-$PID-$ITEM_ID`. This permission is problematic in Flatpak as the `$PID` value is often the same in sandboxes … the `--own-name=org.kde.*` permission will allow this", which "introduces many new risks". "Current versions of Electron, Chromium, KNotifications, and libappindicator are known to work without ownership permissions." [Flatpak docs: desktop integration](https://github.com/flatpak/flatpak-docs/blob/master/docs/desktop-integration.rst)
- Flathub: "All `--own-name` in finish-args are blocked by default unless it exactly matches Flatpak ID or is an exact subname of the Flatpak ID or is a subname of MPRIS", and "This exception is never granted". [Flathub linter docs](https://docs.flathub.org/docs/for-app-authors/linter#finish-args-own-name-cpt). `--talk-name=org.kde.StatusNotifierWatcher` isn't flagged by the linter ([finish_args.py](https://github.com/flathub-infra/flatpak-builder-lint/blob/master/flatpak_builder_lint/checks/finish_args.py)).
- ksni claims `org.kde.StatusNotifierItem-{pid}-{n}` unless `disable_dbus_name(true)`, which "violates the StatusNotifierItem specification, but is required in some sandboxed environments (e.g., flatpak)". [ksni service.rs L57–L72](https://github.com/iovxw/ksni/blob/master/src/service.rs#L57-L72), [blocking.rs L27–L66](https://github.com/iovxw/ksni/blob/master/src/blocking.rs#L27-L66). The measurement run confirms that Slint registers under the owned name (`org.kde.StatusNotifierItem-975675-1`).
- **Consequence:** in a Flathub build, Slint 1.18.1's `SystemTrayIcon` will most likely fail at `request_name` and silently show nothing. Slint master is unchanged ([ksni.rs on master](https://github.com/slint-ui/slint/blob/master/internal/core/items/system_tray/ksni.rs), still `tray.spawn()`). *This is inferred from the source and the docs. It was not run inside a Flatpak, since there's no `flatpak` on this machine.*
- **Ways around it:**
  1. Use [`tray-icon`](https://github.com/tauri-apps/tray-icon) 0.26.1 with its `ksni` feature. That backend calls `.assume_sni_available(true).disable_dbus_name(util::is_sandboxed())` ([src/platform_impl/ksni/mod.rs L51–L53](https://github.com/tauri-apps/tray-icon/blob/dev/src/platform_impl/ksni/mod.rs#L51-L53)) and "manages its own worker thread" (README). Its default Linux backend is GTK 3 + libappindicator and needs a GTK event loop on the thread, which doesn't fit Slint.
  2. Use `ksni` directly with `disable_dbus_name(ashpd::is_sandboxed())` and `assume_sni_available(true)`, and forward events with `slint::invoke_from_event_loop`. ksni is already in the dependency tree whenever Slint's tray is enabled.
  3. Patch Slint upstream to do (2) inside `SystemTrayIcon`.

  Options 1 and 2 give up the declarative `.slint` tray and menu, but they work the same in native and Flatpak builds.
- This qualifies one benefit [ADR-0008](../adr/0008-slint-gui-toolkit.md) lists for Slint ("a tray icon"). As shipped, it holds for native packages but not for Flathub.

### Cost

- **Binary** (measured, section 6): adding `system-tray` grows the stripped release probe from 13,630,088 to 14,762,584 bytes (**+1.08 MiB**). The Slint winit backend already links `zbus` for the XDG settings portal and AccessKit ([winit backend Cargo.toml](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/winit/Cargo.toml)), so the tray adds ksni and the dbusmenu code, not a second D-Bus stack.
- **RAM** (measured): the tray build was 0.5–1.6 MiB PSS above the plain build across three runs. In the first run it was 3 MiB *below* it, so the difference is within run-to-run noise. It adds 2–3 threads.
- `tray-icon`'s size and RAM weren't measured.
- An icon or tooltip that changes every second (live vitals) sends SNI change signals to the tray host every second. The cost on the host side (plasmashell, gnome-shell) wasn't measured.

## 2. Hidden window

- **Closing hides by default:** `CloseRequestResponse::HideWindow` is the default response to a close request. `KeepWindowShown` rejects the close. [api.rs L454–L464](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/api.rs#L454-L464)
- **The loop survives without windows** if the app uses `run_event_loop_until_quit()` (since 1.4.0, "for daemon-style programs"), or keeps a visible tray icon. [slint lib.rs L258–L265](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/slint/lib.rs#L258-L265), [CHANGELOG 1.4.0](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md)
- **What `hide()` does:** "Wayland doesn't support hiding a window, only destroying it entirely". On Wayland (or with `SLINT_DESTROY_WINDOW_ON_HIDE`), Slint suspends the renderer (FemtoVG clears its GL context) and drops the winit window. It keeps the attributes and size so it can recreate the window on `show()`. On X11 it only unmaps the window. [winitwindowadapter.rs L783–L806, L1724–L1738](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/winit/winitwindowadapter.rs#L1724-L1738). The component, its properties and the Rust state all survive, so 1 Hz property updates continue while the window is hidden and show up on the next `show()`. Neither a hidden nor a minimized window renders frames. The toolkit spike measured 0 frames while minimized on KWin ([spike results](https://github.com/tobytaken/prism-electron/blob/prototype/toolkit-spike/prototypes/toolkit-spike/measure/results.txt)).
- **Measured cost** (section 6; AMD RX 460, headless GNOME Shell 50 on Wayland, not NVIDIA):

| State | PSS | anon PSS | VRAM (amdgpu fdinfo) |
|---|---|---|---|
| Visible | 61.0–65.9 MiB | 20.1–23.8 MiB | 22.7 MiB |
| Minimized (`set_minimized(true)`) | 61.2 MiB | 20.1 MiB | 22.7 MiB (unchanged) |
| Hidden after being shown | 60.3–65.4 MiB | 19.7–23.8 MiB | 22.7 MiB (same as first shown) |
| Re-shown | +1.5–2 MiB | | 25.9 MiB |
| **Started hidden, never shown** | **55.4–55.8 MiB** | 18.3 MiB | **13.9 MiB** |

  - Hiding a window that has been shown gives back no measurable RAM, and returns VRAM only to the level of the first shown window. The baseline GL/EGL allocations remain.
  - Over 4 hide/show cycles, anon PSS grew about 1.2 MiB per cycle (20.1 → 25.2 MiB). The run didn't check whether this levels off.
  - The process still opens a DRM client (13.9 MiB VRAM) before any window is shown.
  - The spike's NVIDIA numbers are higher in absolute terms (80.5 MiB PSS, 35 MiB VRAM idle). How hiding behaves on NVIDIA **wasn't measured**.
- **First show after a hidden start doesn't draw** (Wayland). A window that starts hidden and gets `show()` later never rendered in 50 s, even with a property changing every second. Calling `window.request_redraw()` after `show()` fixed it: VRAM and PSS rose to the visible level within 5 s (section 6). This matches [slint#13640](https://github.com/slint-ui/slint/issues/13640) (open), "window first shown after startup draws no frame until an unrelated redraw". Later `show()` calls of a window that was shown before work.
- **Bringing the window back** needs a way in: a tray click, the app launcher, a notification, or GNOME's background-apps list. Launching again from the app menu starts a second process unless Prism enforces a single instance. Slint has no single-instance support. The usual approach is to own the app-ID bus name (`io.github.tobytaken.Prism`, which Flatpak grants by default, according to the linter's "finish-args-unnecessary-appid-own-name: This is granted by default") and implement `org.freedesktop.Application` (`Activate`, `ActivateAction`) with `DBusActivatable=true`. The same interface is what notification `app.` actions (section 4) and GNOME's background-apps "quit" button ([backgroundApps.js](https://gitlab.gnome.org/GNOME/gnome-shell/-/blob/main/js/ui/status/backgroundApps.js)) call. Prism could implement it with the `zbus` already in its tree.
- **Window activation on Wayland:** Slint 1.18.1 never passes an XDG activation token when it recreates a window. There is no `activation_token` use in the winit backend, although winit supports one ([winit startup_notify.rs](https://github.com/rust-windowing/winit/blob/v0.30.13/src/platform/startup_notify.rs)). Whether the compositor raises the recreated window or only flags it ("Prism is ready") when it is opened from the tray or a notification **wasn't tested**.
- **Interaction with edit holds:** an edit hold "ends when those edits are applied or discarded, or when that session closes" ([CONTEXT.md](../../CONTEXT.md), ADR-0005). A GUI that hides instead of quitting keeps its `prismd` session open. Any staged edits would then hold automatic switching on that GPU indefinitely, unless hiding discards them or asks first.

## 3. Autostart

### Native packages (deb, rpm, AUR) and AppImage: XDG autostart

- `.desktop` files in `$XDG_CONFIG_DIRS/autostart` (system: `/etc/xdg/autostart/`) and `~/.config/autostart/` are started at login. A user file with the same name overrides the system one, and `Hidden=true` disables it. [Desktop Application Autostart Specification](https://specifications.freedesktop.org/autostart-spec/latest/)
- An opt-in "Start with the session" setting usually writes or removes `~/.config/autostart/<app-id>.desktop`, with an `Exec` flag such as `--hidden`. CoreCtrl's documented setup is literally `cp /usr/share/applications/org.corectrl.CoreCtrl.desktop ~/.config/autostart/` ([CoreCtrl wiki: Setup](https://gitlab.com/corectrl/corectrl/-/wikis/Setup)). A package-installed `/etc/xdg/autostart` file would start Prism for every user unless each one opts out.
- systemd user sessions turn these files into units through `systemd-xdg-autostart-generator` (`xdg-desktop-autostart.target`). [man page](https://www.freedesktop.org/software/systemd/man/latest/systemd-xdg-autostart-generator.html). On Hyprland, XDG autostart only runs under uwsm. Otherwise it's an `exec-once` in the user's config ([Hyprland wiki: uwsm](https://github.com/hyprwm/hyprland-wiki/blob/main/content/useful-utilities/uwsm.md)). Plain sway was not checked.
- For an AppImage, the `Exec` line has to point to the AppImage's current path, which breaks when the file moves. This is general knowledge, not checked against a source.

### Flatpak: Background portal

- `org.freedesktop.portal.Background.RequestBackground(parent_window, {reason, autostart, commandline, dbus-activatable})` returns `background` and `autostart` booleans. `SetStatus({message})` (version 2) sets a ≤96-character status line. [Background.xml](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.Background.xml). In Rust: `ashpd::desktop::background::Background::request().auto_start(true).command(..)` ([ashpd 0.13 docs](https://docs.rs/ashpd/0.13.13/ashpd/desktop/background/index.html)).
- The frontend writes `~/.config/autostart/<app-id>.desktop` itself, rewriting `Exec` to a `flatpak run …` command with `X-Flatpak=<app-id>`. [background.c `enable_autostart_sync`](https://github.com/flatpak/xdg-desktop-portal/blob/main/desktop-portal/background.c), [xdp-app-info-flatpak.c `validate_autostart`](https://github.com/flatpak/xdg-desktop-portal/blob/main/shared/xdp-app-info-flatpak.c). Flathub won't grant `--filesystem=xdg-config/autostart` "as an Autostart portal exists" ([linter docs](https://docs.flathub.org/docs/for-app-authors/linter#finish-args-arbitrary-autostart-access)).
- **Permission:** the first request sets the permission to "yes" without a dialog. "Ask" shows "Allow %s to Run in the Background?", and "no" refuses. [background.c `handle_request_background_in_thread_func`](https://github.com/flatpak/xdg-desktop-portal/blob/main/desktop-portal/background.c). For host (non-sandboxed) apps, the permission is always "yes". Autostart then needs a detectable app ID, and `SetStatus` is refused ("Only sandboxed applications can set background status").
- **Which desktops implement it:** GNOME (`xdg-desktop-portal-gnome`) and KDE (`xdg-desktop-portal-kde`) list `org.freedesktop.impl.portal.Background` ([gnome.portal](https://gitlab.gnome.org/GNOME/xdg-desktop-portal-gnome/-/blob/main/data/gnome.portal.in), [kde.portal](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/blob/master/data/kde.portal)). COSMIC's portal ([cosmic.portal](https://github.com/pop-os/xdg-desktop-portal-cosmic/blob/master/data/cosmic.portal)), the Hyprland and wlr portals ([hyprland.portal](https://github.com/hyprwm/xdg-desktop-portal-hyprland/blob/master/hyprland.portal), [wlr.portal](https://github.com/emersion/xdg-desktop-portal-wlr/blob/master/wlr.portal)) and the GTK fallback ([gtk.portal.in](https://github.com/flatpak/xdg-desktop-portal-gtk/blob/main/data/gtk.portal.in)) do not. **On COSMIC and wlroots compositors, a Flatpak Prism can't enable its own autostart.**

### How GNOME treats background apps

- The portal's monitor compares the compositor's per-app window state with **running Flatpak instances only**, once a minute. Apps with no window are "in the background". If the permission is "no", the app is killed. Otherwise the backend is asked to notify the user. [background.c implementation notes and `check_background_apps`](https://github.com/flatpak/xdg-desktop-portal/blob/main/desktop-portal/background.c)
- GNOME's backend answers that request with "allow" and shows nothing ([xdg-desktop-portal-gnome background.c `handle_notify_background`](https://gitlab.gnome.org/GNOME/xdg-desktop-portal-gnome/-/blob/main/src/background.c)). Since GNOME 44, Quick Settings instead lists "apps which have been detected to be running without an open window … Currently only Flatpak apps are included" ([GNOME 44 release notes](https://release.gnome.org/44/)). The entry shows the `SetStatus` message. Clicking it calls `app.activate()`, and its close button tries the app's `quit` action and falls back to `flatpak kill` ([backgroundApps.js](https://gitlab.gnome.org/GNOME/gnome-shell/-/blob/main/js/ui/status/backgroundApps.js)). On stock GNOME, which has no tray, this list is the only built-in way back into a hidden Flatpak Prism.
- **Native apps without a window are invisible to GNOME:** they're neither listed nor killed.
- KDE's backend allows silently by default. With `NotifyBackgroundApps` off, it shows a "Background Activity" notification with Allow/Deny ([xdg-desktop-portal-kde background.cpp](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/blob/master/src/background.cpp)).

## 4. Desktop notifications

### `org.freedesktop.Notifications` directly (`notify-rust`)

- Actions are key/label pairs, and the key `"default"` is the click on the notification itself. Servers may not support actions (check the `actions` capability). Invoked actions come back as the `ActionInvoked(id, action_key)` signal, optionally preceded by `ActivationToken(id, token)` for Wayland activation. [Notification spec 1.3: basic design](https://specifications.freedesktop.org/notification-spec/latest/basic-design.html), [protocol](https://specifications.freedesktop.org/notification-spec/latest/protocol.html). The `desktop-entry` hint ties the notification to the app's `.desktop` file ([hints](https://specifications.freedesktop.org/notification-spec/latest/hints.html)).
- The signal goes to the sending connection, so **actions only work while the sending process is alive**. `notify-rust` 4.18.2 (default feature `z` = zbus) exposes this as a blocking `NotificationHandle::wait_for_action` ([src/xdg/mod.rs L99–L115](https://github.com/hoodie/notify-rust/blob/main/src/xdg/mod.rs)) and ignores `ActivationToken`.
- **Flatpak:** needs `--talk-name=org.freedesktop.Notifications`, which the Flathub linter doesn't flag ([finish_args.py](https://github.com/flathub-infra/flatpak-builder-lint/blob/master/flatpak_builder_lint/checks/finish_args.py)).
- **Cost** (measured): +330,624 bytes (**+0.32 MiB**) on the Slint probe, because Slint already links zbus. Tray plus notify-rust: +1.39 MiB.

### Notification portal (`ashpd`)

- `AddNotification(id, {title, body, icon, priority, default-action, default-action-target, buttons, display-hint, category, …})`. "Notifications are expected to outlast the running application. If a user clicks on a notification after the application has exited, it will get activated again." **Actions named `app.*` are activated by D-Bus activation through `org.freedesktop.Application.ActivateAction`** (with an activation token and target). Other actions arrive as `ActionInvoked` on the running app. [Notification.xml](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.Notification.xml) (version 2 since xdg-desktop-portal 1.19.1, [NEWS](https://github.com/flatpak/xdg-desktop-portal/blob/main/NEWS.md)). In Rust: `ashpd::desktop::notification::NotificationProxy` ([ashpd 0.13 docs](https://docs.rs/ashpd/0.13.13/ashpd/desktop/notification/index.html)). ashpd's size and RAM weren't measured.
- **Backends:** GNOME implements it in `xdg-desktop-portal-gnome` ([gnome.portal](https://gitlab.gnome.org/GNOME/xdg-desktop-portal-gnome/-/blob/main/data/gnome.portal.in)), and KDE in plasma-workspace's `plasmanotify` portal ([plasmanotify.portal](https://github.com/KDE/plasma-workspace/blob/master/libnotificationmanager/plasmanotify.portal)). COSMIC and Hyprland fall back to the GTK portal (`default=cosmic;gtk;`, `default=hyprland;gtk`), which implements Notification ([cosmic-portals.conf](https://github.com/pop-os/xdg-desktop-portal-cosmic/blob/master/data/cosmic-portals.conf), [hyprland-portals.conf](https://github.com/hyprwm/Hyprland/blob/main/assets/hyprland-portals.conf), [gtk.portal.in](https://github.com/flatpak/xdg-desktop-portal-gtk/blob/main/data/gtk.portal.in)).
- **Host apps** can use it too: the notification permission is only checked for sandboxed apps ([notification.c L1088](https://github.com/flatpak/xdg-desktop-portal/blob/main/desktop-portal/notification.c)). The portal needs the app's ID, though. A native Prism would register it through `org.freedesktop.host.portal.Registry.Register` (xdg-desktop-portal ≥ 1.19.4) "before any portal method call" ([Registry.xml](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.host.portal.Registry.xml)).

### Do "Open Prism" and "Resume" work?

| Path | Prism running (hidden or tray) | Prism not running |
|---|---|---|
| `notify-rust` (fdo), native or Flatpak | Yes. Prism handles `default`/`resume` from `ActionInvoked`. | No. The click goes nowhere. |
| Portal, non-`app.` actions | Yes, through `ActionInvoked`. | No. |
| Portal, `app.open` / `app.resume` + `DBusActivatable=true` + `org.freedesktop.Application` | Yes | **Yes.** The desktop starts Prism through D-Bus activation and calls `ActivateAction`. In Flatpak, the `.service` file is exported from the app. |

"Resume" means a `prismd` write. It works only if the clicking user has tuning access ([ADR-0011](../adr/0011-prismd-authorizes-each-request.md)). Otherwise Prism has to show why it can't resume.

## 5. Notifications without the GUI

- **`prismd` has no session bus.** It's a root system service, started before login ([ADR-0002](../adr/0002-host-wide-startup-behavior.md)). To notify, a root process has to authenticate to each user's `/run/user/UID/bus` as that user. `systemd-run --user --machine=USER@.host` exists for exactly this ("useful to connect to a specific user's user bus", [systemd-run(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html)). It would also have to enumerate active graphical sessions through logind, decide which users get a host-wide event, and keep a connection per user to receive actions.
- **What the comparable projects do:**
  - **LACT** (root daemon, GUI client): no tray, no notifications. The maintainer: "the background lact service runs as root and is not part of the desktop session … would require running a separate process just for the icon … there can easily be a case where the icon is not running, while the service is" ([LACT#576 comment](https://github.com/ilya-zlobintsev/LACT/issues/576#issuecomment-2887692900), [LACT#358](https://github.com/ilya-zlobintsev/LACT/issues/358) closed as not planned; [LACT#665](https://github.com/ilya-zlobintsev/LACT/issues/665) open).
  - **CoreCtrl:** the GUI *is* the session-side process. It has a Qt tray, "close to tray", "start minimized on system tray" (`--minimize-systray`, `startOnSysTray`), and autostart by copying its desktop file ([app.cpp](https://gitlab.com/corectrl/corectrl/-/blob/master/src/app/app.cpp), [wiki: Setup](https://gitlab.com/corectrl/corectrl/-/wikis/Setup)). Its root helper "kills himself when no signals are received from the application" (same `app.cpp`). There are no desktop notification calls in `src/` (no `showMessage`, KNotification or `org.freedesktop.Notifications`).
  - **GameMode:** `gamemoded` runs per user on the session bus (`systemctl --user`, [README](https://github.com/FeralInteractive/gamemode/blob/master/README.md)) and escalates through polkit. It has no notifications of its own, but because it runs in the session, its config suggests `start=notify-send "GameMode started"` ([example/gamemode.ini](https://github.com/FeralInteractive/gamemode/blob/master/example/gamemode.ini)).
  - **power-profiles-daemon:** a system-bus service. GNOME Shell's Quick Settings reads and sets `ActiveProfile` over the system bus ([powerProfiles.js](https://gitlab.gnome.org/GNOME/gnome-shell/-/blob/main/js/ui/status/powerProfiles.js)). The daemon itself doesn't notify.
  - **earlyoom** (root) once ran `notify-send` and replaced it with a system-bus signal plus a per-user relay, [systembus-notify](https://github.com/rfjakob/systembus-notify): "You need to have systembus-notify running in your GUI session for notifications to work" ([README changelog 1.6](https://github.com/rfjakob/earlyoom/blob/master/README.md), [earlyoom#183](https://github.com/rfjakob/earlyoom/issues/183)).
- **What fits Prism:** `prismd` already pushes events to any local connection and keeps a boot-scoped Activity list ([ADR-0010](../adr/0010-event-driven-daemon-state.md)). Its socket is `0666` with read-only sessions for users who can't tune ([ADR-0011](../adr/0011-prismd-authorizes-each-request.md)). So any process in the user's session can subscribe and turn events into notifications without new daemon privileges. That process is either the GUI kept alive (hidden or in the tray) or a separate small agent. A windowless `notify-rust` sender waiting for an action measured **2.0 MiB PSS / 3.9 MiB RSS, 5 threads, 1.8 MB binary** (section 6). A real agent also needs the prismd protocol client, and that wasn't measured. Whether a `prism --agent` mode of the GUI binary stays this small, as long as it never initializes Slint, **wasn't measured**.

## 6. Measurements on this machine

Measured on 2026-10-10 on Ubuntu 26.04.1 (kernel 7.2.9) with an AMD Radeon RX 460 (amdgpu, Mesa 26.0.8 radeonsi) and an Intel UHD 630. The compositor was GNOME Shell 50.1 started as `gnome-shell --headless --wayland --no-x11 --mode=ubuntu --virtual-monitor 1920x1080` inside `dbus-run-session`. Ubuntu mode loads `ubuntu-appindicators`, so a real SNI host and `org.freedesktop.Notifications` were present. **This isn't the target hardware** (NVIDIA + KDE in the toolkit spike), so absolute numbers differ, but the differences between variants carry over.

- **Probe:** a 900×600 Slint 1.18.1 window (`Text` + `Path`) whose properties change every second, run with `run_event_loop_until_quit()`, plus an optional `SystemTrayIcon` with a two-item menu and an optional `notify-rust` notification. Features are as in the spike (`std`, `compat-1-2`, `backend-winit`, `renderer-femtovg`, `accessibility`). The release profile uses fat LTO, `codegen-units=1`, `strip`, `panic=abort`, rustc 1.99. Environment variables control the hide, show and minimize times, hide/show cycling, a hidden start and an explicit `request_redraw()`.
- **Metrics:** RSS/PSS/USS/anon PSS from `/proc/PID/smaps_rollup`, thread count, and VRAM/GTT from the DRM fdinfo (`drm-memory-vram`), sampled a few seconds after each state change.
- **Binary sizes (stripped):** base 13,630,088 B; `+system-tray` 14,762,584 B; `+notify-rust` 13,960,712 B; both 15,092,312 B. A standalone `notify-rust` sender is 1,871,632 B.
- **Runs:** two passes of visible → hidden (20 s) → re-shown (50 s) and visible → minimized for the base and tray builds; one pass of 4 hide/show cycles at 10 s each per build; a hidden start with `show()` at 25 s per build; a hidden start with `show()` at 10 s, with and without `request_redraw()`. The results are in the table in section 2.
- **Not measured:** NVIDIA (VRAM on hide), a real Flatpak sandbox, `tray-icon`, `ashpd`, a prismd-connected agent, tray-host CPU for per-second icon updates, and window activation from a tray or notification.
