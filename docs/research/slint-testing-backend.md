# What Slint's testing backend can do for Prism's view-layer tests

Research for [What can Slint's testing backend do for Prism's view-layer tests?](https://github.com/tobytaken/prism-electron/issues/118), part of the [native rewrite map](https://github.com/tobytaken/prism-electron/issues/96).
Gathered 2026-10-10 from primary sources: Slint's source, changelog, docs and CI at tag [`v1.18.1`](https://github.com/slint-ui/slint/tree/v1.18.1) (the current release, 2026-09-21, and the version the toolkit spike used), docs.rs, and the test suites and CI of other Slint apps. Claims link to their source. Claims marked **(verified)** were also checked with a throwaway experiment, described in [section 7](#7-experiment).

## Answer in one paragraph

Slint has no `slint::testing` module. The testing API is the separate crate **`i-slint-backend-testing`**, which its own README calls a "preliminary" API that does **not follow semver** and must be pinned with `=x.y.z` to the exact Slint version. Within that limit it covers what Prism's view layer needs. It runs a window with no display. It finds elements by qualified id, type name, accessible role, accessible label or a predicate. It reads every accessible property (role, label, value, min/max/step, checked, enabled, read-only, and more). It invokes the default, increment, decrement, expand and set-value actions, and simulates click, double-click, drag and scroll on mocked or real time. Keyboard input goes through the stable `Window::dispatch_event`. All element lookup needs Slint **debug info** compiled in. Without it, every query silently finds nothing. The same backend renders headless to pixels when it is built with the software or Skia renderer, and `Window::take_snapshot()` returns an RGBA buffer. The software renderer's output was bit-identical on two Linux images with very different system fonts, because Prism names its embedded fonts explicitly. So screenshot tests in CI are practical, as long as the reference images belong to one Slint version and one renderer, and that renderer is not FemtoVG, which Prism ships with. An accessibility baseline audit is a short test that walks the element tree, but it can't list which `accessible-action-*` handlers a widget declares, so each action is checked by invoking it and observing the effect.

## 1. What the API is, and how stable it is

- **Where it lives.** The testing API is the crate `i-slint-backend-testing`, not a module of `slint`. The `slint` crate's public modules at 1.18.1 include `platform`, `language`, `winit_030`, `fontique_011`, `wgpu_29`/`wgpu_30` and `android`, but no `testing` module. [api/rs/slint/lib.rs](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/slint/lib.rs). Docs: [docs.rs/i-slint-backend-testing/1.18.1](https://docs.rs/i-slint-backend-testing/1.18.1/i_slint_backend_testing/). The Slint docs site has no guide page for it. The crate README is the documentation.
- **Stability.** The README says: "This library is an **internal** crate … This crate does not follow the semver convention for versioning and can only be used with `version = \"=x.y.z\"`". It also says: "Preliminary Slint Testing API … may introduce breaking changes in any patch release. Additionally, the version of this crate must match the version of Slint." [internal/backends/testing/README.md](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/README.md). Slint's workspace pins `i-slint-core` and the backends with `=1.18.1` [Cargo.toml L91–96](https://github.com/slint-ui/slint/blob/v1.18.1/Cargo.toml#L91-L96). A `slint` that resolves to a different patch release than the testing crate therefore pulls two `i-slint-core` versions. In practice **`slint` must be pinned with `=` too**, and the two are bumped together. Moosync pins `i-slint-backend-testing = "=1.17.1"` next to `slint = "1.17.1"` ([Cargo.toml](https://github.com/Moosync/Moosync/blob/main/Cargo.toml)), and sed-manager-rs pins both with `=1.17.1` ([Cargo.toml](https://github.com/petiaccja/sed-manager-rs/blob/main/Cargo.toml)).
- **The API has been reasonably steady.** The `ElementHandle` search API, the three `init_*` functions and `mock_elapsed_time` are the same at 1.17.1 and 1.18.1. The 1.18 changes were behavior fixes, such as: "Testing: `ElementHandle`'s click, hover, drag and scroll now aim at the transformed center of an element". [CHANGELOG.md L280](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md#L280)
- **Cargo features of the testing crate** [Cargo.toml](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/Cargo.toml):
  - none (the default): the mock backend with no pixels, plus the search API.
  - `renderer-software` / `renderer-skia`: a real rasterizer inside the testing window, so `take_snapshot()` works (section 3).
  - `internal`: "only enabled for Slint's own tests". It adds `send_keyboard_string_sequence`, `send_mouse_click`, `configure_test_fonts` and others ([lib.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/lib.rs), [internal_tests.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/internal_tests.rs)). Prism shouldn't depend on it.
  - `system-testing` and `mcp`: these are normally enabled through `slint`'s features of the same names. They are remote-control servers (section 6).

### Initialization and threading

From [lib.rs L29–87](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/lib.rs#L29-L87):

| Function | Event loop | Time | Scope |
|---|---|---|---|
| `init_no_event_loop()` | none: `invoke_from_event_loop` and `Timer`s don't run | mocked; advance with `mock_elapsed_time()` | "each test thread can use its own backend", so plain parallel `#[test]`s work **(verified)** |
| `init_integration_test_with_mock_time()` | yes | mocked | "can only be called once per process" |
| `init_integration_test_with_system_time()` | yes | real | once per process; needed for the `async` click and drag helpers, which wait on real `Timer`s |

Apps that need the event loop work around the once-per-process limit with one runner thread that owns the event loop and receives each test through `invoke_from_event_loop` + `spawn_local`. Moosync does this ([ui/slint/src/test_utils.rs](https://github.com/Moosync/Moosync/blob/main/ui/slint/src/test_utils.rs)), and so does sed-manager-rs ([tests/smoke/test_utils.rs](https://github.com/petiaccja/sed-manager-rs/blob/main/sed_manager_gui/sed_manager_gui/tests/smoke/test_utils.rs)).

## 2. Finding elements, reading values, acting

All of this is in [search_api.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs). The roots are any `ComponentHandle` (`ElementRoot` is implemented for every generated component).

- **Finding.**
  - `ElementHandle::find_by_accessible_label(&app, "…")`.
  - `find_by_element_id(&app, "App::power")`: the id is `Component::local-id`.
  - `find_by_element_type_name(&app, "Stepper")`: this also matches base types.
  - `ElementQuery::from_root(&app).match_descendants().match_id(…) / match_type_name(…) / match_inherits(…) / match_accessible_role(AccessibleRole::Spinbox) / match_predicate(|e| …)`, ending in `find_first()` / `find_all()`.
  - `visit_descendants(…)` walks the tree.

  The walk **skips invisible items** and **descends into open popups** ([L370–395](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs#L370-L395), [`active_popups` L1121](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs#L1121)). A handle found by the instance id (`App::power`) reads the custom widget's root accessible properties **(verified)**.
- **Debug info is required.** Element counts, ids and type names exist only when the Slint compiler emits debug info: `SLINT_EMIT_DEBUG_INFO=1` at build time, or `slint_build::CompilerConfiguration::with_debug_info(true)`. That method is `#[doc(hidden)]` and documented as "primarily used by `i-slint-backend-testing`" ([api/rs/build/lib.rs L229–235](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/build/lib.rs#L229-L235)). Without debug info, `collect_elements` yields **zero** elements and only logs a warning ([L62](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs#L62), [L330](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs#L330)). That includes the search by accessible label, so tests "pass" vacuously unless they assert that something was found. In the experiment, a build without debug info visited 0 descendants **(verified)**. Slint's own CI sets `SLINT_EMIT_DEBUG_INFO: 1` for its test jobs ([build_and_test_reusable.yaml L84](https://github.com/slint-ui/slint/blob/v1.18.1/.github/workflows/build_and_test_reusable.yaml#L84)). Its `todo` example's test silently returns when the variable is missing ([examples/todo/rust/lib.rs L172](https://github.com/slint-ui/slint/blob/v1.18.1/examples/todo/rust/lib.rs#L172)). Prism shouldn't copy that.
- **Reading.**
  - `accessible_role`, `accessible_label`, `accessible_value`, `accessible_value_minimum/maximum/step`, `accessible_checked`, `accessible_checkable`, `accessible_enabled`, `accessible_read_only`, `accessible_description`, `accessible_placeholder_text`, `accessible_id`, `accessible_expanded/expandable`, `accessible_item_selected/selectable/index/count`, `accessible_orientation`, `accessible_live_region`.
  - Geometry: `size`, `absolute_position`, `computed_opacity`. Debug info: `id`, `type_name`, `bases`, `layout_kind`.

  There is **no getter for keyboard focus**, and none for the list of supported actions (see section 4).
- **Acting through accessibility.** `invoke_accessible_default_action`, `invoke_accessible_increment_action`, `invoke_accessible_decrement_action`, `invoke_accessible_expand_action`, `set_accessible_value(…)` (which runs `accessible-action-set-value`), and `set_accessible_selection_offsets`. These run the widget's `accessible-action-*` handlers directly. In the experiment, increment and set-value on a Prism-style `Stepper` changed its pending value **(verified)**. Invoking an action the widget doesn't declare does nothing and reports nothing.
- **Pointer input.**
  - `async single_click`, `double_click` and `drag(target)` wait on real timers, so they need an event loop.
  - `mock_single_click` and `mock_drag` are synchronous on mocked time. They are public and need no feature flag, though the docs describe them as being "for our internal tests" ([L988–1110](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs#L988-L1110)).
  - `scroll(dx, dy)`.

  All of them aim at the element's center. `drag` steps 5 px every 16 ms, under the 8 px drag threshold. That suits the power-limit drag and fan-curve points, but a drag to a specific point *inside* a chart needs raw events.
- **Raw events and keyboard.** `slint::Window::dispatch_event(WindowEvent::{PointerMoved, PointerPressed, PointerReleased, PointerScrolled, KeyPressed, KeyReleased})` is stable public `slint::platform` API. It works under the testing backend, and it is what the spike already used. A click to focus followed by `KeyPressed { text: Key::UpArrow.into() }` reached the focused `FocusScope` **(verified)**. slint-node-editor's integration tests drive keys and pointers the same way on `init_no_event_loop` ([integration-tests/tests/common/harness.rs](https://github.com/tilladam/slint-node-editor/blob/main/integration-tests/tests/common/harness.rs)).
- **Other test hooks.** `mock_elapsed_time(Duration)` advances animations and timers and runs change handlers ([testing_backend.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/testing_backend.rs)). `set_system_accent_color` sets the accent. There is **no public setter for the system color scheme**, so `Palette.color-scheme` stays `unknown` under the testing backend ([internal/core/context.rs L252–268](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/context.rs#L252-L268)). Tests must set the Appearance mode to Light or Dark explicitly. "System" can't be simulated.
- **Text measurement in the mock backend.** The README still says "No pixels are rendered and text is measured by a fixed font size". At 1.18.1 that is true only for the font family `FixedTestFont`. Every other family goes through the real parley text layout ([testing_backend.rs L140, L540–570](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/testing_backend.rs#L540-L570)). Layouts in the testing backend therefore use Prism's real fonts.

## 3. Rendering a window headless, and how deterministic it is

- **API.** `slint::Window::take_snapshot() -> Result<SharedPixelBuffer<Rgba8Pixel>, PlatformError>` is stable public API since 1.7, and needs `std` since 1.18 ([internal/core/api.rs L832–838](https://github.com/slint-ui/slint/blob/v1.18.1/internal/core/api.rs#L832-L838), [CHANGELOG L274](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md#L274)). With the plain mock backend it returns `Err("WindowAdapter::take_snapshot is not implemented by the platform")` **(verified)**.
- **Headless rasterizer in the testing backend.** `TestingBackendOptions` has a `renderer_name` field when the testing crate is built with `renderer-software` or `renderer-skia`. `"software"` picks Slint's software renderer. `"skia"` picks Skia's CPU raster (`SkiaRenderer::default_software`) ([testing_backend.rs L152–160](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/testing_backend.rs#L152-L160), [L725–755](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/testing_backend.rs#L725-L755)). The field was already present at 1.17.1. `TestingBackend` and `TestingBackendOptions` are exported "so the backend selector can instantiate the headless backend" ([lib.rs L15–17](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/lib.rs#L15-L17)), so this is reachable but not a documented entry point. The calls are `slint::platform::set_platform(Box::new(TestingBackend::new(TestingBackendOptions { mock_time: true, threading: false, renderer_name: Some("software".into()) })))`, then `app.show()`, then `app.window().take_snapshot()`. This rendered a 360×220 Prism-style window (Inter + JetBrains Mono, a `Path` chart, a hard offset shadow) with no display, under both renderers **(verified)**.
- **Stable alternative.** A custom `slint::platform::Platform` with `MinimalSoftwareWindow` and the software renderer is the documented 1.x way to render without a windowing system. `slint-viewer --screenshot out.png [--size WxH] [--load-data data.json] file.slint` installs exactly such a headless platform ([tools/viewer/screenshot.rs L47–55](https://github.com/slint-ui/slint/blob/v1.18.1/tools/viewer/screenshot.rs#L47-L55); `--size` is new in 1.18). Slint renders its own store screenshot with it in CI ([screenshots.yaml](https://github.com/slint-ui/slint/blob/v1.18.1/.github/workflows/screenshots.yaml), [scripts/make-screenshots.sh](https://github.com/slint-ui/slint/blob/v1.18.1/scripts/make-screenshots.sh)). It works for a `.slint` file with data, not for Rust-implemented globals and callbacks.
- **Renderer differences.** The software renderer has "No support for rotations or scaling", "No support for `drop-shadow-*` properties", and "No support for `border-radius` in combination with `clip: true`" ([backends_and_renderers.mdx L73–85](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/guide/backends-and-renderers/backends_and_renderers.mdx#L73-L85)). In the experiment, the software snapshot left out a `drop-shadow` that Skia drew **(verified)**. That matters for C · Tracks' hard pop-up shadow if it is a `drop-shadow`; a second offset `Rectangle` renders everywhere. `Path` is supported with `std` (the `path` feature is implied). Neither headless renderer is **FemtoVG**, which Prism ships. FemtoVG needs an OpenGL context from a real window, so screenshot tests check layout and drawing logic, not production pixels.
- **Skia's cost.** `renderer-skia` pulls in `skia-bindings`. In the experiment it downloaded prebuilt Skia binaries at build time and linked `-lstdc++ -lfontconfig -lfreetype`. A cold debug build of the test target came to a little over 2 GB. The software renderer is pure Rust apart from fontconfig.
- **Determinism, as Slint itself treats it.** Slint's screenshot suite ([tests/screenshots](https://github.com/slint-ui/slint/tree/v1.18.1/tests/screenshots)) keeps **separate reference PNGs per renderer** (`references/software`, `references/skia`, …). The comparison passes if the maximum per-pixel color distance is under a threshold: 0.1 by default for the software renderer, **4 for Skia on Linux and Windows**, and **33 for Skia on macOS** ("tagging the raster target as sRGB puts Skia on its color managed pipeline, whose float math rounds slightly differently between the Linux and the Windows build") ([testing.rs L131–138](https://github.com/slint-ui/slint/blob/v1.18.1/tests/screenshots/testing.rs#L131-L138), [skia.rs L103–108](https://github.com/slint-ui/slint/blob/v1.18.1/tests/screenshots/skia.rs#L103-L108)). `SLINT_CREATE_SCREENSHOTS=1` rewrites a failing reference but still fails the run. Slint's tests make fonts deterministic with `configure_test_fonts()`, which disables system fonts and registers bundled Noto fonts, but that function is behind the `internal` feature ([lib.rs L103](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/lib.rs#L103)).
- **Fonts and Prism.** Slint always creates its font collection with `system_fonts: true`, through fontconfig on Linux ([internal/common/sharedfontique.rs L19–21](https://github.com/slint-ui/slint/blob/v1.18.1/internal/common/sharedfontique.rs#L19-L21)). Text whose `font-family` names an embedded font (Prism's named text styles), with glyphs that font contains, does not depend on the machine. The experiment rendered the same window in `rust:1-bookworm` (6 system fonts) and `rust:1-trixie` (279 system fonts, including DejaVu and Noto). The software-renderer RGBA buffers hashed identically (`ebf26ab3b7314617`) **(verified)**. Two leaks remain. A glyph missing from Inter or JetBrains Mono falls back to whatever the host has. Text with no `font-family` uses the window's `default-font-family`, or the system sans if that is unset. Renderer fixes also move pixels between Slint releases, for example "Software renderer: Fixed uneven gaps between glyphs" in 1.18 ([CHANGELOG L113](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md#L113)).

## 4. Checking the widget accessibility baseline automatically

The baseline from [How are C · Tracks' design tokens and widgets built in Slint?](https://github.com/tobytaken/prism-electron/issues/106) is that every widget declares `accessible-role`, label, value (min/max/step where relevant), checked state and `accessible-action-*`.

- **What a test can assert directly.** Walk `app.root_element().query_descendants().match_predicate(|e| role is not None).find_all()`. For each handle, require the properties its role implies: a non-empty `accessible_label` for every interactive role; `accessible_value` plus min/max/step for `spinbox` and `slider`; `accessible_checkable`/`accessible_checked` for `switch` and `checkbox`; `accessible_read_only` for read-only controls. Report each failure with `id()` and `type_name()`. In the experiment, this audit flagged a deliberately unlabeled `button` as `App::bad / BadButton` **(verified)**.
- **Text elements count too.** Plain `Text` elements report the `text` role with their text as the label. A role filter that keeps "everything except none" includes them **(verified)**. The audit should check an explicit set of interactive roles.
- **What it can't assert.** `ElementHandle` doesn't expose an element's *supported* actions. The internal `supported_accessibility_actions` is not surfaced ([search_api.rs](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/search_api.rs)), and invoking an undeclared action is a silent no-op. "Declares its actions" is therefore tested per widget: invoke default, increment, decrement or set-value, and assert the effect, such as the pending value, the checked state or a captured intent. Focus order and the keyboard-only focus ring aren't visible through this API either. The ring shows up only in a screenshot or in the widget's own exported state.
- **Coverage.** The walk sees only what is visible, and popups only while they are open. The audit has to run per view state: each GPU fixture, each **prismd connection** reason, read-only versus editable, and menus, pop-ups and dialogs opened.
- **Role vocabulary.** `AccessibleRole` at 1.18.1 has `none, button, checkbox, combobox, groupbox, image, list, slider, spinbox, tab, tab-list, tab-panel, text, table, tree, progress-indicator, text-input, switch, list-item, radio-button, radio-group, window-title-bar`, plus landmark roles (`banner, complementary, content-info, form, main, navigation, region, search`) ([internal/common/enums.rs L466](https://github.com/slint-ui/slint/blob/v1.18.1/internal/common/enums.rs#L466)). It has **no `menu`, `menu-item`, `dialog`, `tooltip` or `alert` role**, so Prism's `Menu`, `Dialog`, `Tooltip` and `Popover` need a documented choice of fallback role, or `none`.

## 5. What other Slint apps do

- **Slint's own examples.** `examples/todo` has one `#[test]`. It uses `init_no_event_loop`, finds a line edit by id, calls `set_accessible_value`, presses the "Add New Entry" button through `invoke_accessible_default_action`, and asserts on the Rust model ([lib.rs L171–199](https://github.com/slint-ui/slint/blob/v1.18.1/examples/todo/rust/lib.rs#L171)). `examples/todo-mvc` puts logic in controllers with a `MockTaskRepository` and tests them without any UI. That is the same split as `prism-ui` plus a simulated provider ([task_list_controller.rs](https://github.com/slint-ui/slint/blob/v1.18.1/examples/todo-mvc/rust/src/mvc/controllers/task_list_controller.rs)).
- **Slint's CI.**
  - The language and screenshot suites run with `SLINT_EMIT_DEBUG_INFO=1` on hosted runners, with no display server for these tests.
  - The visual editor's UI tests run the real binary with `--features slint/mcp` and `SLINT_BACKEND: headless-skia`, driven over MCP by a private Python package ([ci.yaml L83–134](https://github.com/slint-ui/slint/blob/v1.18.1/.github/workflows/ci.yaml#L83-L134)).
  - The Python bindings' tests use `SLINT_BACKEND: testing` ([python_test_reusable.yaml L25](https://github.com/slint-ui/slint/blob/v1.18.1/.github/workflows/python_test_reusable.yaml#L25)).
- **Moosync** (Slint 1.17.1, GPL-3.0, about 260 stars). It has `rstest` fixtures with `init_no_event_loop` and integration tests on one event-loop runner thread with `init_integration_test_with_system_time`. Tests find by accessible label ("Toggle Sidebar", "Back"), click, then poll app globals with `wait_until` ([navigation_test.rs](https://github.com/Moosync/Moosync/blob/main/ui/slint/src/integration_tests/navigation_test.rs)). CI is Bazel on `ubuntu-24.04` ([tests.yaml](https://github.com/Moosync/Moosync/blob/main/.github/workflows/tests.yaml)).
- **sed-manager-rs** (Slint `=1.17.1`). It has smoke tests on a shared event-loop thread, an `ElementHandle` extension trait, and a 30 s per-test timeout. CI runs `xvfb-run -a cargo test` on Ubuntu and plain `cargo test` on Windows ([build_and_test.yml](https://github.com/petiaccja/sed-manager-rs/blob/main/.github/workflows/build_and_test.yml)).
- **slint-node-editor** (Slint 1.18). Its integration-test harness calls `init_no_event_loop` once per thread and drives the editor with `Window::dispatch_event` for keys and pointers ([harness.rs](https://github.com/tilladam/slint-node-editor/blob/main/integration-tests/tests/common/harness.rs)).
- None of the apps surveyed keeps pixel references of its own app in CI. A [GitHub code search for `i-slint-backend-testing` in `Cargo.toml`](https://github.com/search?q=i-slint-backend-testing+path%3ACargo.toml&type=code) returns about 35 non-Slint repositories. Screenshot comparison with references is something Slint does for its own renderers.

## 6. Remote-control options (for completeness)

- **MCP server** (`slint` feature `mcp`, added in 1.17.0, [CHANGELOG L506](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md#L506)). Set `SLINT_MCP_PORT` and `SLINT_EMIT_DEBUG_INFO=1`, and an agent can list windows, query the tree, click, drag, type and `take_screenshot`. `SLINT_BACKEND=headless` (or `headless-software` / `headless-skia`) runs it without a display, and the README states: "This is an unstable, MCP-oriented entry point — the exact value of `SLINT_BACKEND` may change between Slint releases. Use it from automation, not from production code." ([testing README](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/README.md), [api/rs/slint/Cargo.toml L119–126](https://github.com/slint-ui/slint/blob/v1.18.1/api/rs/slint/Cargo.toml#L119-L126)). This is useful for agent-driven checks and README screenshots of the real binary, but not as the test suite.
- **System testing** (`slint` feature `system-testing`). The app connects to `SLINT_TEST_SERVER` and speaks a protobuf protocol (find elements, read properties, invoke actions, click, drag, dispatch keys, take a snapshot) ([slint_systest.proto](https://github.com/slint-ui/slint/blob/v1.18.1/internal/backends/testing/slint_systest.proto)). The client side Slint uses in CI is a private package, so it is not an option for Prism.

## 7. Experiment

This was a throwaway crate outside the repo, with Slint `=1.18.1` and `i-slint-backend-testing = "=1.18.1"` (`renderer-software`, optionally `renderer-skia`). `build.rs` called `compile_with_config(…with_debug_info(true))`. The window held a `Stepper` (a `FocusScope` with spinbox role, min/max/step, increment, decrement and set-value actions, and Up/Down keys), a `Toggle` (switch role), an unlabeled `button`, a `Path` chart, mono text with `⋯ ● ■`, and a `drop-shadow` box. The fonts were Inter and JetBrains Mono, imported in `.slint`. It ran under `cargo test` in `rust:1-bookworm` and `rust:1-trixie` containers with no display.

- Search by label, id, type name and role all found the right element. Accessible value, min, max, step and checked read correctly. Increment, set-value and the default action took effect. `mock_single_click` toggled the switch and focused the stepper, and `dispatch_event(KeyPressed UpArrow)` reached it. Tests ran on parallel threads with `init_no_event_loop`.
- The audit flagged exactly the unlabeled button.
- Software and Skia snapshots rendered with no display. The software buffer was identical across the two images. Skia drew the drop shadow and the software renderer didn't.
- A build without debug info found 0 elements, and every lookup came back empty.
- The host needed `pkg-config` and the fontconfig development headers for `fontique`. `RUST_FONTCONFIG_DLOPEN` alone didn't build.
