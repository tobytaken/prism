# The daemon runs fan curves as part of GPU tuning

For [issue #64](https://github.com/tobytaken/prism/issues/64), the host daemon runs applied fan curves independently of the app. A shared cooling configuration governs all fans on a GPU by default, with separate per-fan automatic, fixed-speed, or curve control available. Running curves in the app would make cooling depend on a UI session and conflict with before-login startup tuning. The issue contains the agreed editor behavior, numeric defaults, and acceptance criteria; this ADR records the architectural decisions.

Cooling joins GPU tuning profile scope and existing startup behavior, extending the cooling exclusions in ADR-0001 and ADR-0002. A cooling setting represents its control mode and complete curve or fixed target, not an instantaneous percentage emitted by a curve. Profiles and restoration baselines preserve that configuration, and a restored curve evaluates the current temperature. Omitting cooling from an existing profile continues to leave cooling unchanged.

[Issue #41](https://github.com/tobytaken/prism/issues/41) and its existing follow-up tickets own game-triggered cooling application, restoration, edit holds, manual overrides, and recovery through the shared cooling controller. Issue #64 owns the editor, daemon curve controller, cooling profile representation, remembered curves, startup support, and controller supervision. There is no second game-switching engine or curve evaluation loop. A switching hold or pause defers profile replacement while a healthy applied curve keeps responding to temperature.

Cooling state follows the daemon-owned lifetimes in ADR-0005. Persistent state includes cooling profile settings, startup choices, last applied manual cooling configurations, and each user's remembered curve and fan arrangement per GPU. Same-boot applied-curve recovery and game restoration baselines belong to boot-scoped state; a reboot follows the existing startup choice. Unapplied edits remain session-local. A remembered curve survives switching cooling modes but recalling it only creates a draft. Temporary game curves and routine curve output changes never replace the remembered manual choice or last applied manual tuning values.

Custom curve control requires known fan-speed bounds and a trustworthy GPU maximum operating temperature. Curves must reach the maximum supported speed at least 5°C before that boundary. If those capabilities are unavailable, custom curves are unavailable with an explanation and automatic cooling remains available. This deliberately favors a verifiable control range over broader support based on guessed limits. A zero-percent request is permitted only when supported and does not establish physical fan stop.

Sensor or fan-command failure attempts default automatic control for the affected GPU, suspends curve control, preserves the curve, and requires explicit retry. Recovery also covers service stops, crashes, and hangs through supervision outside the curve loop; process exit must not be assumed to reset fan policy. NVIDIA's [fan command documentation](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceCommands.html) puts temperature monitoring on the caller after manual speed writes and exposes a separate operation for restoring default control. Recovery outcomes are reported per fan and remain conditional on the host and driver accepting commands.

If another setting fails after cooling was successfully changed by a game profile, the existing switching recovery flow restores the previous complete cooling configuration. If cooling itself failed, its automatic-control fallback takes precedence: rollback must not silently restart a faulted curve without explicit retry. This refines ADR-0004's recovery contract to distinguish profile switching from the ongoing temperature response of a healthy curve.

A detected external control change suspends Prism's curve control while leaving the external controls alone; resumption requires explicit user action. Within Prism, a cooling change made by another session preserves an open draft but requires review before that draft can replace the changed configuration. Opening or editing a control does not acquire control of cooling, and ordinary curve output changes are not competing user edits.

These are agreed design decisions; the fan curve implementation is tracked in issue #64.
